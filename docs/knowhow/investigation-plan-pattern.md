# 調査計画の実行パターン（計画01総括）

## 発見した知見

計画01（プロジェクト全体探索と knowhow 整備）の総括。1セッション内で探索〜knowhow 9本〜品質ゲート〜完了処理まで完遂できた。

### 効いた設計判断

- **分割軸は「機構単位」**（レートリミット / ロール / 可視性 / チャンネル / 連合 / モデレーション）にし、ディレクトリ単位にしなかった。後続計画（実装計画の策定）が機構単位で立つため、knowhow がそのまま計画の脚注になる
- **各探索エージェントに「改造意図」を渡した**（例:「意図POST予算制を計画している。その下調べとして」）。単なる現状調査ではなく「変更ポイント候補 + 落とし穴」まで返ってくるので、knowhow の実用性が大きく上がる
- **「事実と推測を区別して書け」の指示**は報告の信頼性評価を容易にした。全エージェントが遵守した

### 正確性の信頼境界（レビュー結果からの実測）

- リポジトリ内コードに関する file:line 付き主張: レビューで突合された範囲では**全て正確**（9ファイル、数十件）
- 誤りが出たのは2箇所のみ: **外部 npm パッケージの内部仕様への断定**（High）と**引用範囲の行数を根拠にした個数の主張**（Medium。88行≠88種）。「エージェント報告のうち、リポ外の挙動と集計値は自前検証してから書く」が教訓

### 計画とのギャップ

- 当初懸念した「upstream との diff が巨大で棚卸し不能」問題は発生しなかった。**squash merge 統合方式のおかげで origin/develop..HEAD が27コミットに収まっており、コミット履歴がそのまま機能一覧になった**。統合フローの理解が棚卸しを一撃で解決した（先に統合スクリプトを読むのが正解だった）

## プロジェクトへの適用

- 今後の調査系計画（新領域の下調べ）はこのパターンを踏襲する: 機構単位分割 × 改造意図の注入 × 事実/推測区別 × 完了通知ごとの即 knowhow 化
- 探索エージェントの成果を検収するときは「リポ外の挙動」「集計値」の2種だけ重点検証すればよい

## 注意点・制約

- 探索7本の並列実行はサブエージェントのトークン消費が大きい（1本あたり5〜11万トークン）。小さな調査なら分割数を絞る
