# 計画10: 連合停止と閉鎖インスタンス化

## 実装状況: 未着手

## 目的

イヴの時間構想「実装の基盤」の実現:

> **連合（ActivityPub federation）は行わない**。他インスタンスへの迷惑になる可能性が高く、また連合越しの投稿には本構想の制約が及ばないため、実験の前提が壊れる。閉じたワンオフのインスタンスとして運営する。

連合越しの投稿にはレートリミット・成熟モデル・Deliberation Gate のいずれも及ばない。連合が1ミリでも開いていると「すべての参加者は同じ制約を受ける」（空間のルール2）が成立しないため、本計画は他のすべての機構計画（レートリミット・非ログイン閲覧制限等）の土台であり、**最初に着手する計画**である。

設計態度は構想に従う: 技術は舞台装置であり、完璧な強制力は求めない。目標は「連合が誤って再有効化されない・対外的に連合機能が見えない」状態を、小さいパッチで確実に成立させることである。

本計画は2フェーズ構成をとる:

- **Phase 1（本計画のスコープ）**: 既存の `federation: 'none'` 設定を基点に、抜け穴を塞ぐ小パッチ数個で閉鎖を成立させる
- **Phase 2（本計画では方針のみ）**: 稼働実績を得てから AP コード約6,400行を段階的に物理削除する。詳細は将来の独立計画に委ねる

## 現状の挙動

一次資料: [docs/knowhow/federation-shutdown.md](../knowhow/federation-shutdown.md)（file:line 付き調査済み）

### 既存設定でほぼ止まる

- `Meta.federation: 'all' | 'specified' | 'none'` が存在し、**デフォルトが 'none'**（`packages/backend/src/models/Meta.ts:686-697`）。セットアップウィザードにも「連合なし」の選択肢がある（`MkServerSetupWizard.vue:61-77`）
- 判定の一次点は `UtilityService.isFederationAllowedHost` / `isFederationAllowedUri`（`packages/backend/src/core/UtilityService.ts:134-148`）
- `'none'` で 403 になるもの: AP エンドポイント全15箇所（inbox / outbox / users / notes の AP 表現等、`packages/backend/src/server/ActivityPubServerService.ts`）+ WellKnown 4箇所（webfinger / host-meta / `.well-known/nodeinfo`、`packages/backend/src/server/WellKnownServerService.ts`）
- inbox 処理・AP 解決・deliver 実行（Processor 側）も `isFederationAllowedHost` 経由で全て遮断される
- フロントエンドは `instance.federation === 'none'` を見てナビ・ウィジェット・連合統計等を自動非表示にする（対応済み）

### 残っている抜け穴（本計画で塞ぐ対象）

1. **管理 UI / `admin/update-meta` から `federation` を戻せる**。`.config/*.yml` に連合を封じる設定は存在せず、真実の源は DB の Meta のみ（`packages/backend/src/server/api/endpoints/admin/update-meta.ts:203-207`（paramDef）、`:758-767`（適用処理））。誤操作ひとつで実験の前提が崩れる
2. **`/nodeinfo/2.0` `/2.1` 直リンクにはガードが無い**。`NodeinfoServerService.ts` は federation を一切参照しない（403 になるのは `.well-known/nodeinfo` だけ）。ルート登録は `packages/backend/src/server/NodeinfoServerService.ts:137, 152`
3. **deliver ジョブの enqueue は止まらない**。`ApDeliverManagerService.execute`（`packages/backend/src/core/activitypub/ApDeliverManagerService.ts:107-148`）→ `QueueService.deliver` / `deliverMany`（`packages/backend/src/core/QueueService.ts:146-223`）にガードが無く、Processor 側で skip されるだけ。過去のリモートフォロワーが DB に残っていると空回りのジョブが積まれ続ける
4. **HTML の `/users/:user` `/notes/:note` は生きる**（Accept ヘッダの `apOrHtml` constraint で分岐）。ただしこれは「連合停止」ではなく「対外公開制御」の軸であり、`Meta.ugcVisibilityForVisitor`（`Meta.ts:703`）を扱う**計画11（非ログイン閲覧制限）のスコープ**。本計画では触らない
5. 連合と無関係の外部通信が残る: Web Push（VAPID、`Meta.enableServiceWorker` / `swPublicKey`、`Meta.ts:357, 363`）、URL プレビュー（`Meta.urlPreviewEnabled`、`Meta.ts:651`）、メディアプロキシ、SMTP（`Meta.enableEmail`、`Meta.ts:318`）

### Meta のロード経路（変更点1の設計に必要な知識）

Meta（サーバー設定）は DB から2経路でロードされ、runtime 中は pubsub で更新される:

- **DI 経由の常駐インスタンス**: `GlobalModule.ts` の `$meta` プロバイダ（`packages/backend/src/GlobalModule.ts:100-` 付近）が起動時に DB から読み、`metaUpdated` 内部イベント（Redis pubsub）でプロパティをその場更新する。各サービスは `@Inject(DI.meta)` で参照する
- **MetaService のキャッシュ**: `packages/backend/src/core/MetaService.ts` の `fetch()`（:66-99、5分間隔の再読込あり）と `onMessage()`（:46-64、`metaUpdated` 受信）

つまり「Meta ロード時オーバーライド」は、**この2経路×（初期ロード＋pubsub 更新）の全代入点**に適用しなければ、update-meta 実行後の runtime 値がすり抜ける。

### config の追加方法（変更点1の設計に必要な知識）

`.config/default.yml` は `pnpm compile-config` で JSON にコンパイルされ、`loadConfig()`（`packages/backend/src/config.ts:244`）が読む。新キーの追加は `config.ts` の `Source` 型（:26）・`Config` 型（:120）・`loadConfig()` の返却オブジェクトの3箇所＋`.config/example.yml` への記載で完結する。migration は不要。

## 変更内容

### 1. config 独自フラグ `closedInstance` による federation 恒久ロック

**方針**: DB（Meta）より上位の真実の源として、config ファイルに閉鎖フラグを置く。config はデプロイ成果物であり、管理 UI からの誤操作・単発の DB 書き換えでは覆らない。

- **`packages/backend/src/config.ts`**:
  - `Source` 型（:26〜）に `closedInstance?: boolean;` を追加
  - `Config` 型（:120〜）に `closedInstance: boolean;` を追加
  - `loadConfig()`（:244〜）の返却オブジェクトに `closedInstance: config.closedInstance ?? false,` を追加
  - デフォルト `false`: フラグ未設定の既存テスト・開発環境の挙動を変えない
- **`.config/example.yml`**: `closedInstance: true` の記載例とコメント（「閉鎖インスタンスモード。federation を 'none' に強制固定する」）を追加
- **オーバーライドヘルパー**: `packages/backend/src/misc/apply-closed-instance.ts`（新規、SPDX ヘッダー要）に以下を実装:
  ```ts
  export function applyClosedInstance(meta: MiMeta, config: Config): MiMeta {
      if (config.closedInstance) {
          meta.federation = 'none';
          meta.federationHosts = [];
      }
      return meta;
  }
  ```
- **適用点（4箇所すべて必須）**:
  1. `GlobalModule.ts` `$meta` プロバイダの初期ロード直後（factory 内。`DI.config` を inject に追加）
  2. 同プロバイダ内の `metaUpdated` イベントハンドラでプロパティコピー後
  3. `MetaService.fetch()` のキャッシュ代入前（2つの return 経路とも）
  4. `MetaService.onMessage()` の `metaUpdated` 処理でキャッシュ再構築後

  ※ `MetaService` には `@Inject(DI.config)` を追加する

- **`packages/backend/src/server/api/endpoints/admin/update-meta.ts`**（:758-767 付近）: `closedInstance` 有効時は `ps.federation` / `ps.federationHosts` を**無視する**（エラーにはしない）。オーバーライドだけでも runtime 値は守られるが、DB に 'all' が書き込まれた状態を放置すると「DB と runtime の不一致」という時限的な混乱の種になるため、書き込み自体を止める
  - paramDef・res スキーマは変更しない（API 表面の変更を避け、misskey-js 再生成を不要にする）

これにより、`/api/meta` や `/api/federation/*` 系のレスポンス・フロントエンドの `instance.federation` 参照はすべて自動的に 'none' を報告し、既存のフロントエンド側の連合 UI 非表示ロジックがそのまま効く。

### 2. nodeinfo 直リンクの 403 化

- **`packages/backend/src/server/NodeinfoServerService.ts`**: `@Inject(DI.meta)` を追加し、`/nodeinfo/2.1`（:137）と `/nodeinfo/2.0`（:152）のハンドラ冒頭に以下を追加:
  ```ts
  if (this.meta.federation === 'none') {
      reply.code(403);
      return;
  }
  ```
- 判定は config フラグ直接ではなく `meta.federation === 'none'` を見る（変更点1のオーバーライドにより config が真実の源になっているため。また、フラグ無しで手動 'none' 運用しているケースでも塞がるのが正しい挙動）
- `.well-known/nodeinfo` は既に `WellKnownServerService` で 403 になっているため変更不要

### 3. deliver enqueue の短絡

- **`packages/backend/src/core/QueueService.ts`**: `@Inject(DI.meta)` を追加し、`deliver()`（:147〜）と `deliverMany()`（:189〜）の冒頭に `if (this.meta.federation === 'none') return null;`（`deliverMany` は `return;`）を追加
- enqueue の最下流である `QueueService` で塞ぐことで、`ApDeliverManagerService.execute()`（:107-148）を含む全呼び出し元を一括でカバーする。呼び出し元83箇所の `apRendererService` 呼び出し（レンダリングの無駄）は残るが、それは Phase 2 の削除対象であり、Phase 1 では「キューにゴミが積まれない」ことだけを保証する
- `ApDeliverManagerService.execute()` 側にも冒頭ガード（`this.meta.federation === 'none'` なら即 return）を追加してよい。リモートフォロワーの DB クエリ（followings 検索）も省けるため実害の軽減になる。ただし必須は QueueService 側

### 4. 連合非依存の外部通信の扱い（方針の明文化。コード変更なし）

以下は**連合ではなく、閉鎖インスタンス自身の利用者に向いた機能**であり、本計画では止めない:

| 通信 | 判断 | 理由 |
|---|---|---|
| Web Push（VAPID） | 残す | 参加者への通知。既存の `enableServiceWorker` 設定で運用者が制御可能 |
| URL プレビュー | 残す | 参加者の閲覧体験。`urlPreviewEnabled` で制御可能 |
| メディアプロキシ | 残す | 外部画像の安全な表示。閉鎖性と矛盾しない |
| SMTP（メール） | 残す | 招待・通知に使う可能性。`enableEmail` で制御可能 |

これらを「閉鎖」の名の下に止めると空間の使い勝手だけが下がる。閉鎖の目的は「制約の及ばない投稿経路を無くすこと」であり、アウトバウンドの利便機能は目的と無関係である。運用上さらに静かにしたい場合（スキャナからの 403 可視性を含む）はリバースプロキシ側で塞ぐ選択肢があるが、それは運用判断でありコードのスコープ外。

### 5. Phase 2（AP コード段階削除）の段取り方針 — 本計画では実装しない

upstream 追従の放棄（2026-07-03 決定）により、AP コードの物理削除は正当な選択肢になった（「破壊して綺麗にする」方針とも合致）。ただし規模が大きい:

- AP 関連コード約6,400行 + `apRendererService` 呼び出し83箇所 + Note/User エンティティのカラム（uri / inbox / publicKey 等）への浸潤
- エンティティのカラム削除は migration を伴う

**段取り方針**（将来の独立計画 `docs/plans/` に切り出す。着手条件: Phase 1 適用後のインスタンスが安定稼働していること）:

1. サーバールート層の削除（`ActivityPubServerService` / WellKnown の AP 部分）— 外形的な攻撃面の消滅
2. 配送層の削除（`ApDeliverManagerService` / deliver・inbox キュー / `apRendererService` 呼び出し83箇所）
3. 解決層の削除（`ApResolverService` / リモートユーザー・ノート解決）
4. エンティティカラムの削除（migration 必須。各ステップで `pnpm --filter backend check-migrations` を通す）

各段階でビルド・テストを通し、壊れたら該当段階だけ戻せる粒度を保つ。Phase 1 の変更（本計画）は Phase 2 完了後に一部不要になる（deliver 短絡はコードごと消える）が、config フラグと update-meta ガードは「Meta 設定として federation が残る限り」有効なまま維持する。

## テスト方針

前提: `cp .github/misskey/test.yml .config/test.yml`

1. **unit テスト（`pnpm --filter backend test`）**:
   - `applyClosedInstance()`: フラグ true で `federation` が 'all'/'specified' でも 'none' に強制されること、false で素通しになること
   - `QueueService.deliver` / `deliverMany`: `meta.federation === 'none'` のとき enqueue せず null / undefined を返すこと（deliverQueue のモックで add / addBulk が呼ばれないことを検証）
2. **e2e テスト（`pnpm --filter backend test:e2e`）**: 既存の連合系 e2e が `federation: 'none'`（test.yml デフォルト構成）で従来どおり通ること。可能なら以下を追加:
   - `/nodeinfo/2.0` `/nodeinfo/2.1` が federation 'none' 時に 403 を返す
   - `admin/update-meta` で `federation: 'all'` を送っても（closedInstance 有効時）`/api/meta` の `federation` が 'none' のままである
   - ※ e2e はプロセス起動時の config を共有するため、closedInstance 有効ケースのテストが既存スイートと同居できない場合は unit 側（オーバーライド適用点のテスト）でカバーし、e2e は手動確認に置き換えてよい
3. **手動確認（実インスタンス）**: `closedInstance: true` で起動し、(a) `.well-known/webfinger` / `.well-known/nodeinfo` / `/nodeinfo/2.0` / `/users/:id`（Accept: AP）がすべて 403、(b) 管理 UI で連合設定を変更しても反映されない、(c) ノート投稿時に deliver キュー（管理 UI のジョブキューダッシュボード）にジョブが積まれない、を確認する
4. **品質ゲート**: `pnpm lint` / `pnpm build` / `pnpm --filter backend test`。entity 変更なしのため `check-migrations` は現状維持確認のみ

## 破壊的変更の許容範囲

- upstream 追従は放棄済み。破壊的変更に制約はない
- ただし Phase 1 はあえて**最小パッチ**にとどめる。理由は保守性への遠慮ではなく工数対効果: 閉鎖の成立自体は小パッチで足り、大規模削除は「動いてから」の方が安全に行えるため（knowhow の段取り推奨に従う）
- `closedInstance` 有効時に管理者が federation 設定を変更できなくなるのは意図した破壊であり、許容する
- ワンオフ・閉鎖・招待制の運用形態のため、この変更で困る外部利用者は存在しない
