# 計画15: アカウント成熟モデル

## 実装状況: 未着手

## 目的

イヴの時間構想・技術2「アカウント成熟モデル（Memory Gate）」を実装する。

- 参加資格は「永続する記憶＝継続的な責任」だが、記憶の保有は入口では証明できない。よって Memory Gate は**入口の門ではなく継続評価**として実装する（構想の決定）
- 新規アカウントは低い制限（より少ない投稿回数・少ない権限）から始まり、実績に応じて権限が育つ
- 複数アカウントによるレートリミット迂回への対策を兼ねる。防衛線は招待制（Misskey 既存機能）

**スコープの明確化（構想の決定に基づく）**: 「文脈の一貫性」の高度な評価方法（機械的な指標か、モデレーターの判断か）は**走らせてから運用の中で決める**——先に指標を固定しない。したがって本計画が扱うのは**時間・投稿数ベースの機械的成熟のみ**である。意味的・文脈的な評価（文体の一貫性、話題への参加度など）は将来計画（計画18: 記憶を持つモデレーター、またはその後続）に委ねる。本計画の成熟モデルはその土台となる「権限が段階的に育つ器」を用意するものと位置づける。

## 現状の挙動

### rateLimitFactor（既存ポリシー・罠あり）

- `rateLimitFactor`（`RoleService.ts:67`、default 1）は `ApiCallService.call` のレートリミットチェック（`packages/backend/src/server/api/ApiCallService.ts:334-338`）で参照され、`duration * factor` / `max ÷ factor` に効く——**大きいほど厳しい**（名前の直感と逆）
- 集約は `Math.max`（`RoleService.ts:443`）なので**複数ロール兼務時は最も厳しい値が勝つ**。「成熟で factor を下げて緩める」設計は兼務で相殺される
- `factor = 0` は**レートリミット完全免除**（`ApiCallService.ts:336` の `factor > 0` 判定）という危険なエッジがある
- UI 上のレンジは 0.3〜3.0（`packages/frontend/src/pages/admin/roles.policy-editor.vue:12`）

- `meta.disableRegistration`（default `true`）で招待コード必須。招待コードは `MiRegistrationTicket`（code / expiresAt / createdBy / usedBy）

## 変更内容

### 設計原則: 「デフォルト=最も厳しい、ロールは緩和のみ」

priority 集約の罠（boolean は OR、数値は Math.max ——同一 priority では常に緩い方が勝つ）に対して、2通りの組み方がある:

- **(a) 絞るロール方式**: デフォルトは現状のまま、「新参」ロール（`createdLessThan`）を priority 2 で絞る。→ priority 管理を誤ると即座に穴になる。また priority 2 は「そのポリシーについて他のロールを全部無視する」ため、将来ロールが増えるたびに衝突を考える必要がある
- **(b) 緩和ロール方式（採用）**: **ベースロール（`meta.policies`）を「新参の制限値」まで絞り**、「定着」「成熟」の conditional ロールが**緩和だけを与える**。緩和方向なら OR / Math.max 集約が素直に働き、複数ロール兼務でも「最も育った段階の値」が勝つ＝昇格が保証される。priority は全ロール 0（Low）のままでよく、罠を構造的に回避できる

**例外は `rateLimitFactor`**: これだけは「大きいほど厳しい」×「Math.max = 厳しい方が勝つ」で緩和方式が破綻する（成熟ロールで 1.0 を与えても、別ロールの 3.0 に負ける…は正しい挙動だが、「新参だけ 3.0」をベースロールに置くことができない——ベースは全員に効くため）。さらに `factor = 0` 免除の危険エッジもある。**本計画では `rateLimitFactor` を成熟モデルの制御軸として使わない**。段階制御は Phase 2 の新ポリシー（予算値の直接指定）で行う。

### Phase 1: 設定のみで成立する MVP（コード変更ゼロ・計画13 と独立に先行可能）

管理画面（またはメンテナンス API）操作のみ。成果物はこの節の設定値と、適用手順の記録（`docs/knowhow/` への運用ノウハウ追記）。

#### 1-1. 招待制の有効化

- `meta.disableRegistration = true` を確認（default で true。管理画面で開放していないこと）
- 招待発行権限は「成熟」ロールにのみ `canInvite: true` を与える（値は下表）。招待の連鎖速度そのものが空間の成長速度を決めるため、`inviteLimit` は小さく始める
- root（オーナー）は `canInvite` チェックをバイパスするため、初期メンバーの招待はオーナーが直接発行できる

#### 1-2. ベースロール（= 新参の制限値）を絞る

`admin/roles/update-default-policies`（管理画面「ベースロール」）で設定。**既存アカウントも一旦この値に落ちるが、既存アカウントは作成日時・投稿数の条件を満たして「定着」「成熟」ロールに JIT で入るため、実質的な影響は新規アカウントに限定される**（オーナー root はそもそもバイパスが多い）。

#### 1-3. 段階ロールの新設（conditional × 2）

3段階 = 「ベースロール（新参）」+ conditional ロール2本。段階数と閾値は**要オーナー確認**（下記に案として記す）。

| 段階 | 実現方法 | 条件式（案） |
|---|---|---|
| 新参 | ベースロールそのもの（ロール不要） | ——（アカウント作成直後から） |
| 定着 | conditional ロール / priority: Low(0) | `and(createdMoreThan: 7日(604800秒), notesMoreThanOrEq: 10)` |
| 成熟 | conditional ロール / priority: Low(0) | `and(createdMoreThan: 30日(2592000秒), notesMoreThanOrEq: 50)` |

ポリシー値の案（緩和方式なので、各ロールは「その段階で解放される値」だけを Low priority で持つ。未設定項目は useDefault でベースに従う）:

| ポリシー | ベース（新参） | 定着 | 成熟 | 備考 |
|---|---|---|---|---|
| `canPublicNote` | true | — | — | 降格（silence 相当）は成熟モデルでは使わない。処罰系は計画18 |
| `canCreateChannel` | **false** | — | **true** | 空間分割は成熟者の仕事（構想・技術1の人口適応と整合） |
| `canInvite` | false | — | **true** | 招待は成熟者の特権 |
| `inviteLimit` | 0 | — | **3** | `inviteLimitCycle` はデフォルト（7日）のまま |
| `driveCapacityMb` | **50** | **100** | **300** | 新参の攻撃面（大量アップロード）を絞る |
| `antennaLimit` | **1** | **5** | 5 | 全量監視系ツールの構築を成熟前に絞る（ルール3の思想と整合） |
| `webhookLimit` | **0** | **1** | **3** | 外部送信面は成熟に応じて解放 |
| `canImport*`（5種） | false | — | — | 閉鎖インスタンスでは全段階不要のまま |
| `rateLimitFactor` | 1（触らない） | — | — | 前述の理由で成熟モデルの軸に使わない |
| `intentfulPostBudget`（Phase 2 新設） | **3/h** | **5/h** | **8/h** | 下記 Phase 2。値は計画13 の基準値と整合させる |

- `gtlAvailable` / `ltlAvailable` / `canSearchNotes` 等の閲覧系は絞らない。「声を聞くことは参加者に開かれている」（ルール3）——制限するのは**発言と構造操作**であり、閲覧はアカウントを持った時点で全量解放が構想の立場
- MISTEMS 独自ポリシー（`canUseTimemachine` / `timemachineReachableFrom` 等、`RoleService.ts:49-51`）は本計画では現状値のまま。段階制御したくなったら運用で調整（設定のみで可能）

#### 1-4. バッジ・表示

- 「定着」「成熟」ロールに `asBadge: true` を設定するかは**要オーナー確認**。conditional でもバッジは自動反映される（既存機構）ため設定のみで可能。ただし「段階の可視化」は詮索文化（ルール1）を刺激しうる——非表示から始める案を推す

### Phase 2: 意図POST予算の段階制御（コード変更・計画13 に依存）

計画13 が導入する共有予算バケット（`ApiCallService.call()` にフックする「意図の表明」系操作の統一予算）の**予算量をロールポリシーで段階制御**する。

#### 2-1. 新ポリシー `intentfulPostBudget`（数値・時間あたり回数）

- **factor（乗数）ではなく予算回数そのものをポリシー値にする**。理由:
  - `rateLimitFactor` の轍（大きいほど厳しい・Math.max 集約で緩和が兼務相殺・0 = 免除の危険エッジ）を踏まない
  - 予算回数なら `Math.max` 集約 = 「最も育った段階の予算が勝つ」で緩和方式と完全に整合する
  - `0` の意味が「免除」ではなく「予算ゼロ = 意図POST不可」になり、エッジが安全側に倒れる
  - 「残り n 回」の弾数表示（計画14: Deliberation Gate）にそのまま渡せる
- 免除機構は**作らない**。「人間もエージェントも同じ制約」（ルール2）——root すら例外にしない設計を計画13 と合わせて確認する（計画13 側の共有バケットが `rateLimitFactor` を通さない方針とも整合）
- ウィンドウ長（duration）はポリシー化せず計画13 側の単一設定とする。ポリシーで動かすのは回数のみ（人口適応＝計画16 はウィンドウ全体の基準値を動かす。軸を分離する）

#### 2-2. 実装セット（新ポリシー追加のフルセット）

`docs/knowhow/role-policy-mechanics.md` の「新ポリシー追加フルセット」に従う:

1. `RolePolicies` 型に `intentfulPostBudget: number` を追加（`packages/backend/src/core/RoleService.ts:36-79`）
2. `DEFAULT_POLICIES` に既定値を追加（`RoleService.ts:81-130`。既定 = 新参の値になるよう小さく）
3. `getUserPolicies` の集約に `calc('intentfulPostBudget', vs => Math.max(...vs))` を追加（`RoleService.ts:412-463`）
4. enforcement 呼出点: **`IntentBudgetService.resolveLimit()` の内部**で `RoleService.getUserPolicies()` から `policies.intentfulPostBudget` を参照する（計画13 が定めた正規経路。`ApiCallService` 側は改修しない）。人口適応（計画16）との併用時の合成規則は計画13 に定義済み: **最終予算 = min(ロール由来値, 人口ベースライン)**
5. 管理 UI: `packages/frontend/src/pages/admin/roles.policy-editor.vue` に編集 UI（数値入力）を追加、`locales/ja-JP.yml` の `_role._options` にラベル追加（ja-JP.yml のみ編集）
6. **`pnpm build-misskey-js-with-types` で misskey-js 再生成**（RolePolicies は misskey-js と同期必須、`RoleService.ts:35` のコメント）

#### 2-3. Phase 1 設定の更新

新ポリシー実装後、ベースロール / 定着 / 成熟に予算値（案: 3/5/8 回/h）を設定する。値は計画13 の予算基準値（構想では「例: 5回/h」）に対して新参で下回り、成熟で上回る配置とする。

### Phase 3（本計画では実装しない・判断のみ記録）: conditional ロールの制約への対応

以下の制約は認識した上で、**MVP では対応不要**と判断する:

| 制約 | 対応要否 | 理由 |
|---|---|---|
| `assignedAt` が無い（いつ昇格したか記録されない） | 不要 | 昇格日時は条件式から逆算可能（作成日 + N日）。監査需要が出たら将来対応 |
| `admin/roles/users` で member 一覧できない | 不要 | 少人数運用では管理画面の各ユーザー詳細で足りる。全員分の俯瞰が要る規模になったら再考 |
| 昇格通知が飛ばない | **保留（要オーナー確認）** | 「静かな昇格」はむしろ構想に合う（段階を意識させない）。一方、Deliberation Gate の弾数表示（計画14）で予算増加は自然に体感される。通知を出すなら conditional 評価に fanout を足す小改修が必要 |
| 昇格の反映遅延（getUserPolicies 5分キャッシュ） | 不要 | 日・週単位の成熟に対して5分は誤差 |

## 要オーナー確認

1. **段階数**: 3段階（新参/定着/成熟）案でよいか。2段階（新参/成熟）でシンプルに始める選択肢もある（後から段階追加は設定のみで可能なので、迷うなら2段階スタートを推す）
2. **閾値**: 定着 = 7日+10投稿 / 成熟 = 30日+50投稿 の案。毎時数回の空間では投稿数の積み上がりが遅い（5回/h × 1日フル稼働でも120回。実際は数投稿/日と想定）ため、投稿数条件は控えめにしてある。日数と投稿数のバランス感の確認
3. **ポリシー値**: 上表の各値（特に `canCreateChannel` と `canInvite` を成熟のみに置く判断、`inviteLimit: 3`、意図POST予算 3/5/8 回/h）
4. **バッジ表示**: 段階をバッジで可視化するか。詮索文化を刺激しない「非表示」を推すが、成熟の実感（育てた人格の重み＝追放刑の抑止力、構想・技術6）には可視化が効く面もある
5. **昇格通知**: 静かな昇格でよいか、通知を出すか（出すなら Phase 3 相当の小改修が必要）
