# 計画16: 人口適応レートリミットとチャンネル分割

## 実装状況: 未着手

## 目的

イヴの時間構想「技術1: レートリミット = 人間速度」の**人口適応（決定事項）**を実装する。

> レートリミットは固定値ではなく、空間の人の集まり具合に応じて上下させる。人が少ないうちは緩く（タイムラインの死＝コールドスタート問題を防ぐ）、増えるほど絞る。上限の目安はダンバー数的な認知上限。300人前後がオンラインで投稿していく規模までは、投稿が多くても問題ない。この上限に近接したら、チャンネルの仕組みで発言の場を分ける。（イヴの時間構想.md 技術1）

本計画は2つの柱からなる:

1. **人口適応予算**: 計画13の意図POST予算の上限値を、空間のアクティブ投稿者数の関数として動的に決める
2. **チャンネル分割の受け皿**: 認知上限に近接したとき「場を分ける」手段としてのチャンネル機構を、濫立を防いだ状態で待機させる

設計態度は構想に従う: これは検問所ではなく舞台装置である。人口計測が多少ズレても、空間の性格（少人数ではにぎやかに、大人数では言葉を選ぶ）が保たれればよい。

## 依存

- **計画13（レートリミット=人間速度・意図POST予算制）**: 本計画は計画13が新設する予算 Service に「上限値の供給源」として人口係数を注入する。計画13の実装完了が前提。計画13と本計画は並行起草のため、接続点のインターフェース（後述）は計画13確定時に突き合わせて調整すること
- 一次資料: `docs/knowhow/rate-limit-mechanics.md` / `docs/knowhow/channel-mechanics.md` / `docs/knowhow/role-policy-mechanics.md`

## 変更内容

### 1. 「人の集まり具合」の計測 — 比較と推奨

「オンラインで投稿していく規模」（構想）を測る候補:

| 案 | 定義 | 長所 | 短所 |
|---|---|---|---|
| A. `get-online-users-count` 流用 | 直近10分に streaming 接続したユーザー数 | 実装ゼロ | 読み専を含む（投稿者ではない）。10分窓は短すぎて振動する。streaming を張らない API クライアント（エージェント）が漏れる |
| B. `ActiveUsersChart` 参照 | チャート集計の hourly unique write | 既存集計 | チャートエンジンは描画用で、移動窓の値を制御ループから引く用途に不向き。時間境界でしか更新されない |
| C. notes テーブル集計 | `COUNT(DISTINCT userId)` を AID 時刻境界で | 正確 | 毎回 DB スキャン。ノート以外の意図POST（リアクション等）を含まない |
| **D. 予算 Service 併走計測（推奨）** | **直近N時間に意図POSTを1回以上実行したユニークユーザー数**。計画13の予算消費イベントで Redis の時刻バケット Set に `SADD`（例: `intentPop:{unixHour}`、TTL = N+1時間）し、直近Nバケットの `SUNION` サイズ（規模が育てば `PFADD`/`PFCOUNT` に置換可能）で取得 | 「投稿者」の定義が意図POSTの定義とそのまま一致する。予算 Service と同居して自己完結。DB 負荷ゼロ。読み専・bot の空接続を数えない | 計画13完了が前提。導入直後は履歴が無いので緩い側から始まる（コールドスタート方向なので望ましい挙動） |

**推奨は D**。「アクティブ投稿者数 P = 直近N時間に意図POSTを実行したユニークユーザー数」と定義する。N は設定値（叩き台: **N = 6時間**、1時間バケット×6）。10分窓（案A）だと昼夜で予算が激しく波打つが、6時間窓なら「今日この空間で声を出している人数」に近い滑らかな値になる。

案Aの値（オンライン閲覧者数）は捨てない — 密度UI（スコープ外、検討メモ参照）の素材として残る。`get-online-users-count` 自体は既存ウィジェットが使うため変更しない。

### 2. 予算値 = f(人口) の関数設計（叩き台）

パラメータ（すべて設定可能な値とし、初期値は要オーナー確認）:

- `P_max = 300` — ダンバー数的認知上限（構想の決定事項）
- `B_loose = 30/h` — 少人数時の緩い上限（コールドスタート対策）
- `B_tight = 5/h` — 収束下限（構想の「毎時数回（例: 5回）」）

**案イ: 線形補間（連続式）**

```
B(P) = round( B_tight + (B_loose - B_tight) × (1 - min(P / P_max, 1)) )
```

P=0→30/h、P=150→約17/h、P≧300→5/h。単調・説明1行・実装3行。

**案ロ: 階段関数（テーブル）**

| P（アクティブ投稿者） | 予算/h |
|---|---|
| 〜30 | 30 |
| 〜100 | 15 |
| 〜200 | 8 |
| 201〜 | 5 |

連続式より「いま空間はこのフェーズ」という段階の物語性があり、参加者への説明可能性が高い。段の境界で体験が急変するのが欠点。

**叩き台の推奨は案イ（線形）**。滑らかで境界の崖がなく、パラメータ3つで完結する。指数減衰やロジスティックは表現力に対して説明コストが見合わない。最終選択は要オーナー確認。

**振動対策（必須）**:

- P は生値でなく **EMA（指数移動平均）等で平滑化**し、B(P) の再計算はキャッシュ付き（例: 5分間隔）で行う
- **窓の途中で B が下がっても、既に消費済みの分は遡って 429 にしない**（次の消費判定から新しい B を使うだけ）。逆に B が上がれば即座に恩恵を受ける
- Deliberation Gate / 残弾表示（計画13系）が返す `total` は動的値になる。「残り n/m 回」の m が時間帯で変わることは仕様であり、UI 側で異常扱いしない

### 3. 計画13の予算 Service への接続点

新設: **`IntentPopulationService`**（`packages/backend/src/core/` 配下、NestJS injectable）

```
recordIntent(userId)            … 予算消費成功時に呼ばれ、時刻バケット Set に記録
getActivePosterCount(): number  … 直近N時間のユニーク投稿者数（平滑化済み、キャッシュ付き）
getCurrentBudgetMax(): number   … B(P) を返す
```

接続は2箇所:

1. **計画13の予算 Service**（`IntentBudgetService`）が、`resolveLimit()` の内部で `IntentPopulationService.getCurrentBudgetMax()` を参照する。予算消費の成功時に `recordIntent()` を呼ぶ（消費と計測が同一トランザクション的に並ぶので取りこぼしがない）
   - **合成規則（計画13 に定義済み）**: 人口値は全参加者共通のベースライン（天井）であり、`最終予算 = min(ロール由来値（計画15）, 人口ベースライン)`。本サービスが無効のときは `Meta.intentBudgetMax` がベースラインとしてフォールバックする（同カラムは無意味化しない）
2. **残量照会エンドポイント**（計画13で新設予定の `i/rate-limit-status` 相当）の `total` フィールドが動的値を返す。追加の新規エンドポイントは不要（人口そのものを晒す API は作らない — 密度UIが必要になったときに検討）

注意: 計画13と本計画は並行起草のため、Service 名・メソッドシグネチャは計画13の確定版に合わせて**実装着手時に突き合わせる**こと。合意済みの設計原則は「予算チェックは `ApiCallService.call()` の単一フック」「自前カウンタ（peek 可能）」「factor を通さない」の3点で、これは両計画で共有される。

### 4. チャンネル分割の受け皿整備

**(a) `canCreateChannel` のデフォルト false 化**

`packages/backend/src/core/RoleService.ts:99` の `DEFAULT_POLICIES.canCreateChannel: true` を `false` に変更する。

- デフォルト true のまま運用開始するとチャンネルが濫立し、「認知上限に近接したら場を分ける」という**タイミング設計そのものが成立しなくなる**（channel-mechanics.md の第一推奨）
- 管理UIで base role を設定する運用でも同じ効果は得られるが、コードデフォルトの変更は「設定忘れで濫立」の事故を構造的に消す。ワンオフ品・破壊的変更歓迎の方針に合致
- 集約は OR (`RoleService.ts:430`) なので、admin/moderator ロールや専用ロールに `canCreateChannel: true` を付与すれば個別に解放できる。root はポリシーバイパスあり
- フロントは `channels.vue:37` が `$i?.policies.canCreateChannel` を見ているため**変更不要**（作成ボタンが自動的に消える）

**(b) 上限近接時の運用（チャンネル開設の解放）**

- `IntentPopulationService` に近接閾値（叩き台: `P ≧ 0.8 × P_max` = 240人）を持たせ、超過したら**モデレーションログ or system webhook で管理者に通知**する（既存の `SystemWebhookService` を利用）。自動でポリシーを書き換える機構は初期には作らない
- 解放の実体は手動運用: 管理者が「チャンネル開設者」ロール（`canCreateChannel: true`）を信頼できる参加者に付与するか、モデレーターが自らチャンネルを開設して場を分ける
- conditional ロール（`createdMoreThan` 等の JIT 評価、role-policy-mechanics.md）による「成熟アカウントへ自動解放」は将来オプションとして温存。初期は空間の分け方自体が運用判断（トピック分割か時間帯分割か等）を要するため、人間の手に残す

**(c) 全チャンネル横断タイムライン — 作らない（提案）**

現状エンドポイントが無い。本計画では**新設しない**ことを提案する。理由: チャンネル分割の目的は認知負荷の低減であり、横断TLは分けた場を再び1本に混ぜて分割を無効化する。全体の見取り図は (d) の一覧UIが担い、各チャンネルへは HTL へのオプトイン合流（チャンネルフォロー）で足りる。※要オーナー確認に含める

**(d) `MkChannelIndex.vue` の活用**

MISTEMS 独自の全チャンネル一覧（viewMode 3種）を「空間の見取り図」の導線として位置づける。本計画内での改修は最小限（導線の確認のみ）とし、declare されたまま未使用の `hashTags` の整理は実装時に気づきベースで行ってよい。密度表示への拡張は下記スコープ外。

### スコープ外（検討メモ）

**「流速ではなく密度を見せる UI」は本計画のスコープ外**。構想の「それでも静かな時期はある。流速ではなく密度を見せるUI」は独立した設計課題であり、本計画の成果物（アクティブ投稿者数 P、オンライン閲覧者数）はその素材になる。将来計画の叩き台メモ: MkChannelIndex / タイムラインヘッダに「いまこの空間に何人いるか（流速でなく在席感）」を出す、投稿の絶対時刻より相対密度を優先する表示、など。ここでは着手しない。

## テスト方針

- **unit（backend）**: `IntentPopulationService` を重点対象にする
  - B(P) の table-driven テスト（P=0 / 150 / 300 / 300超、クランプ境界）
  - 時刻バケットの窓ずれ（バケット境界を跨ぐユニークカウント、TTL 失効）

  - 自前カウンタ方式なので `NODE_ENV !== 'production'` で RateLimiter が無効になる既存の罠（rate-limit-mechanics.md）の影響を受けない設計とし、dev でもテスト可能にする

- 統合（計画13合流後）: 人口を人工的に注入して予算 max が変わることを、残量照会エンドポイント経由で確認
- 実行前提: `.config/test.yml`（`cp .github/misskey/test.yml .config/test.yml`）。`pnpm lint` / `pnpm --filter backend test` を品質ゲートとする

## 破壊的変更の許容範囲

- upstream 追従は放棄済み。`DEFAULT_POLICIES` の変更・予算 Service への依存注入など、upstream と乖離する変更を躊躇しない
